**How the integration tests work**
- Signing: the test computes `sha256=` plus the HMAC-SHA256 hex from `ApiFactory.WebhookSecret` and the exact UTF-8 bytes it sends. The body is a raw JSON string sent as `ByteArrayContent`, and the header name is the literal `"X-Provider-Signature"`.
- Data: payments are seeded through `AppDbContext`. AutoFixture makes the event ids, amounts, currencies, methods and unknown GUIDs.
- Cleanup: each test deletes the `ProcessedWebhookEvents` rows for the event ids it created, then the `Payments` rows it created.
- Startup test: it uses a separate factory, `factory.WithWebHostBuilder(UseSetting(secret, ""))`, and expects `CreateClient()` to throw `OptionsValidationException`. It also checks that `Failures` contains `"Webhooks:Provider:Secret is required."`.

**Decisions for the implementer to know**
1. Extra theory row. I added a "two header values" row to `Webhook_InvalidSignature_Returns401`: one valid signature and one wrong signature. This tests the plan's D1 rule that more than one header value is invalid, and it catches an implementation that only reads the first value.
2. Null eventId. `Validate_EventIdEmpty_ReturnsEventIdError` passes `null!`, with a comment explaining that a JSON null gets past the reader's required-member check.
3. Startup exception type. If WebApplicationFactory wraps the startup exception instead of throwing `OptionsValidationException` directly, the implementer should report the startup test back to me rather than change the code to fit it.
